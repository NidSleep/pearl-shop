# QY-13: Rate limiting for `/api/checkout` — plan

Status: **v4** (Claude, after Codex review rounds 1–3). Awaiting Codex sign-off.

## Problem

`POST /api/checkout` creates a `pending` order (+ `order_items`) and a Stripe
Checkout Session on every call, with no authentication. A script can call it in
a loop and fill `orders` with junk pending rows and create Stripe sessions.

## Goal / non-goals

- Goal: cap checkout attempts per client IP and reject the excess with HTTP 429
  **before any order/order-item write, product read, or Stripe call**. (The
  limiter itself writes one counter row, including for rejected requests.)
- Non-goals: bot detection/CAPTCHA, per-customer limits (no accounts),
  defending against IP rotation, other routes, cleaning existing pending orders.

## Decision: where to keep the counters

| Option | Pros | Cons |
|---|---|---|
| In-memory `Map` | Zero setup | Useless on Vercel: instances don't share memory |
| Upstash Redis (issue suggestion) | Purpose-built | New account, 2 secrets, new dependency |
| **Postgres (Supabase) table + SQL function** | No new service; atomic in one SQL call | One extra DB round-trip; needs scheduled cleanup |

**Choose Postgres.** One new secret (`RATE_LIMIT_SECRET`, for HMAC) is still
needed — see Privacy.

## Policy

- **5 attempts per 10-minute fixed window, per client IP.** Every call counts,
  including malformed carts, stock errors and downstream failures.
- Fixed window accepted: up to 10 attempts can land around a boundary
  (5 just before + 5 just after).
- Per IP, not per customer: several customers behind one NAT share the quota.
  Monitor 429 rates (server logs) and tune the constants if needed.
- Declined-card retries happen on Stripe's hosted page and do not call this route.

## Trust model for the client IP

- Supported deployment: **Vercel, directly** (no extra proxy in front). Vercel
  overwrites `x-forwarded-for` with the real client IP, so the first entry is
  trustworthy there. Verify with a forged header on the first preview deploy (QY-14).
- Self-hosting is **not** supported by this logic unless a proxy strips and
  rebuilds forwarding headers and the origin is not directly reachable.
  Documented in README.
- Missing IP: in development (`NODE_ENV !== "production"`) use `"dev-local"`;
  in production treat as a configuration error → **503** (fail closed).

## Privacy

- Key = `HMAC-SHA-256(RATE_LIMIT_SECRET, canonicalIp)` (hex). Raw IPs and raw
  headers are never stored or logged. Plain SHA-256 is not used (IPv4 is
  enumerable). The value is still a pseudonymous identifier.
- Retention: buckets are deleted once `window_start` is older than 24 h by an
  **hourly** job, so normal maximum retention is ~25 h. If cron runs fail,
  retention grows until it recovers (see Verification 10 for how to notice).
- `RATE_LIMIT_SECRET`: server-only, ≥32 random bytes, same across instances.
  Added to `.env.example`; rotation simply resets all buckets.
- Missing secret → limiter unavailable → 503 (fail closed).

## Design

### 1. Migration `supabase/migrations/0003_checkout_rate_limit.sql`

Single transaction. Checkout-specific function (constants inside, so different
callers can't share or misconfigure buckets).

```sql
begin;

create table public.checkout_rate_limits (
  key          text        not null check (length(key) = 64),  -- hex HMAC
  window_start timestamptz not null,
  hits         integer     not null default 0,
  primary key (key, window_start)
);
create index checkout_rate_limits_window_start_idx on public.checkout_rate_limits (window_start);

alter table public.checkout_rate_limits enable row level security;  -- no policies
revoke all on public.checkout_rate_limits from public, anon, authenticated;
grant select, insert, update, delete on public.checkout_rate_limits to service_role;

-- Returns one row: allowed, retry_after_seconds (positive int, only meaningful when not allowed).
create or replace function public.check_checkout_rate_limit(p_key text)
returns table (allowed boolean, retry_after_seconds integer)
language plpgsql
security invoker
set search_path = ''
as $$
declare
  c_limit   constant integer := 5;
  c_window  constant integer := 600;  -- seconds
  v_now     timestamptz := pg_catalog.now();
  v_window  timestamptz;
  v_hits    integer;
begin
  if p_key is null or pg_catalog.length(p_key) <> 64 then
    raise exception 'invalid rate limit key';
  end if;

  -- EXTRACT is special SQL syntax: must stay unqualified (resolves to pg_catalog even with search_path = '').
  v_window := pg_catalog.to_timestamp(
    pg_catalog.floor(extract(epoch from v_now) / c_window) * c_window);

  insert into public.checkout_rate_limits as r (key, window_start, hits)
  values (p_key, v_window, 1)
  on conflict (key, window_start) do update set hits = r.hits + 1
  returning r.hits into v_hits;

  allowed := v_hits <= c_limit;
  retry_after_seconds := greatest(1, pg_catalog.ceil(
    extract(epoch from (v_window + pg_catalog.make_interval(secs => c_window) - v_now)))::integer);
  return next;
end;
$$;

revoke execute on function public.check_checkout_rate_limit(text) from public, anon, authenticated;
grant  execute on function public.check_checkout_rate_limit(text) to service_role;

-- Retention: hourly, bounded batch, outside request transactions.
-- Returns rows deleted. 50k/run is far above this shop's expected volume
-- (distinct IPs × 6 windows/hour); if a run hits the cap, the next run continues.
create or replace function public.prune_checkout_rate_limits()
returns integer
language plpgsql
security invoker
set search_path = ''
as $$
declare
  v_deleted integer;
begin
  delete from public.checkout_rate_limits
  where ctid in (
    select ctid from public.checkout_rate_limits
    where window_start < pg_catalog.now() - interval '24 hours'
    limit 50000
  );
  get diagnostics v_deleted = row_count;
  return v_deleted;
end;
$$;
revoke execute on function public.prune_checkout_rate_limits() from public, anon, authenticated;

-- Job runs as the migration user (`postgres` via SQL Editor), which owns the
-- table: owners are not subject to RLS (no FORCE ROW LEVEL SECURITY), so the
-- invoker function can delete. No SECURITY DEFINER needed.
create extension if not exists pg_cron;
select cron.schedule('prune-checkout-rate-limits', '7 * * * *', 'select public.prune_checkout_rate_limits()');

commit;
```

(No `SECURITY DEFINER` anywhere. Cron failures are visible in `cron.job_run_details`.)

### 2. `src/lib/rate-limit.ts` (new, `import "server-only"`)

- `getClientIp(headers)`: first comma-separated entry of `x-forwarded-for`,
  else `x-real-ip`. Trim, reject if > 64 chars, then canonicalize:
  - IPv4 (`isIP() === 4`): use as-is (dotted quad is already canonical).
  - IPv6 (`isIP() === 6`): serialize via `new URL("http://[" + ip + "]/").hostname`
    (WHATWG serializer: lowercase, leading zeros dropped, longest zero run
    compressed), strip brackets. If the result is IPv4-mapped (`::ffff:hhhh:hhhh`),
    convert the last 32 bits to a dotted IPv4 so mapped and plain IPv4 share a key.
  - Anything else (incl. zone IDs `%eth0`) → null.
- `checkCheckoutRateLimit(request)` returns one of:
  - `{ ok: true }`
  - `{ ok: false, status: 429, retryAfterSeconds }`
  - `{ ok: false, status: 503 }` — secret missing, IP missing/invalid in
    production, RPC error, thrown error, malformed result (anything other than
    exactly one row with boolean `allowed` and positive integer
    `retry_after_seconds`), or **timeout (3 s via AbortSignal)**.
- Logs failures with a short reason only (no IP, no key, no headers).

### 3. `src/app/api/checkout/route.ts`

- First statement: `checkCheckoutRateLimit(request)`; before body parsing.
- 429 → `{ error: "Too many checkout attempts. Please wait a few minutes and try again." }`
  + `Retry-After` header.
- 503 → `{ error: "Checkout is temporarily unavailable. Please try again shortly." }`.
- Read headers from `request.headers` (Node runtime default; POST is uncached
  in Next.js 16, no route config needed).

## Verification (no test framework exists in the repo yet)

Scripted, repeatable checks (commands recorded in the PR):

1. `npm run lint && npx tsc --noEmit && npm run build`.
2. Migration applied; `cron.job` has the prune job.
3. **Concurrency:** 20 parallel `POST /api/checkout` with an invalid body and the
   same forged dev IP header → exactly 5 × 400 and 15 × 429; each 429 has a
   positive integer `Retry-After`. Fresh random test IP per run so earlier hits
   don't leak in; run right after a window boundary check (`retry_after_seconds > 30`)
   to avoid straddling a boundary.
4. **Independent keys:** a different test IP is still allowed.
5. **Fail closed:** unset `RATE_LIMIT_SECRET` → 503, and no order rows created.
6. **Permissions:** as `anon` and `authenticated` (SQL `set role`): select on the
   table and execute of both functions are denied.
7. **No raw IP stored:** keys in the table are 64-hex.
8. Normal checkout from the cart still reaches Stripe.
9. **Window reset** (SQL, no waiting): insert a bucket for a test key with
   `hits = 5` and `window_start` = previous window → calling the function is
   allowed (new window, hits = 1). Insert `hits = 5` in the current window →
   denied with `retry_after_seconds` between 1 and 600.
10. **Cleanup actually runs:** insert one expired (25 h old) and one current
    bucket; call `prune_checkout_rate_limits()` as `postgres` → returns ≥ 1,
    expired gone, current kept. After the next hourly tick,
    `cron.job_run_details` shows `status = 'succeeded'` for the job. Failed runs
    show there with `status = 'failed'` (documented in README as the place to check).
11. **RPC failure / malformed → 503:** run the dev server with
    `NEXT_PUBLIC_SUPABASE_URL` pointing at an unreachable host → 503 within ~3 s;
    unit-style check of the result validator with malformed shapes (`[]`, two
    rows, `allowed: "yes"`, `retry_after_seconds: 0`) via a small Node script.
12. **Invalid production IP → 503:** `next build && next start` (production
    mode) with `x-forwarded-for: not-an-ip` → 503.
13. **Rejected requests do no work — with a VALID cart** (an invalid body
    could never reach products/Stripe, so it proves nothing). Add a temporary
    dev log line at the product lookup. Then:
    a. Exhaust a test IP's bucket (SQL: set `hits = 5` in the current window),
       send a valid cart (real product id, qty 1) from that IP → **429**.
    b. With `RATE_LIMIT_SECRET` unset (limiter unavailable), send a valid cart → **503**.
    For both: no product-lookup log line, `orders` row count unchanged, and
    `stripe` CLI / Dashboard shows no new Checkout Session. Remove the log after.

Follow-up (separate Linear issue): add a test runner (e.g. Vitest) and turn
checks 3–6 into automated tests.
